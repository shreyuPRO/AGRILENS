# AGRILENS engineering governance

Applies to every change in this repository from 2026-11-18. The rules are enforced by `tools/governance/agl_governance.py` (rules file `tools/governance/governance_rules.json`), by git hooks and by Kiro hooks, so that version numbers, documentation and the change register do not depend on memory.

## 1. Versioning

### Single source of truth

`APP_VERSION` in `application/main.py` is the only authoritative application version. It stays a literal in `main.py` because every deployed updater (4.9.x and 5.0.x) reads `APP_VERSION` from the downloaded `main.py` to block downgrades. No other file may define the application version independently.

| Value | How it follows `APP_VERSION` |
|---|---|
| About tooltip, status bar, start-up log line, OTA User-Agent, downgrade guard, rollback folder `rollback/v<version>/` | read from `APP_VERSION` at run time |
| `OTA_RELEASE_ID` (`AGRILENS-<version>`), `BUILD_TIMESTAMP` | written by `bump`; checked |
| `README.md`, `HOW_TO.md` | `<!-- agl:version -->` markers written by `bump`; checked |
| `documentation/release_notes/RELEASE_NOTES_<version>.md` | stub created by `bump`; must exist |
| `AGRILENS_RaspberryPi/RELEASE_MANIFEST.json`, `SHA256SUMS` | generated by `deployment/packaging/build_device_package.py` at release time |
| `deployment/release_manifests/AGRILENS-<version>.json` | written by `deployment/packaging/write_release_record.py` at release time |

`python tools/governance/agl_governance.py version` prints every value.

The generated OTA folder `AGRILENS_RaspberryPi/` holds the **published** version. Between releases the source may be ahead of it, never behind it. If the source version equals the package version, every shipped source file must be identical to its package copy. A change to a shipped file without a version increment is refused, because a kiosk on the same version does not pick up the change at boot.

Model identity (`MODEL_ID`, `MODEL_VERSION`, `MODEL_SHA256`, `DATASET_VERSION`) is versioned separately from the application and checked against `models/` and `models/manifests/MODEL_REGISTRY.json`.

### Increment rules (Semantic Versioning)

| Part | Use for | Example |
|---|---|---|
| PATCH | bug fixes, corrections, non-functional improvements | 5.0.0 → 5.0.1 |
| MINOR | new backward-compatible functionality, enhancements, UI changes | 5.0.0 → 5.1.0 |
| MAJOR | architectural or incompatible changes (interfaces, workflow, OTA compatibility) | 5.0.0 → 6.0.0 |

`5.0.1` is taken by the prepared fleet rollback release `AGRILENS-5.0.1-rollback`; the next application patch release is therefore `5.0.2` or later.

Procedure for every implementation task:

1. Inspect the version and git state: `agl_governance.py version`, `git status`.
2. Decide the increment from the scope of the change. Documentation-only, test-only and repository-tooling changes do not change the application version; record "unchanged: <reason>" in the change register.
3. `python tools/governance/agl_governance.py bump <patch|minor|major> --reason "<why>"`. It changes `application/main.py`, the markers and creates the release-notes stub. It never touches `AGRILENS_RaspberryPi/` and refuses a second bump in the same task unless `--force` is given. Each bump is logged in `.git/agrilens/version_log.jsonl`.
4. Record the increment and its rationale in the change-register entry (field "Application version").
5. The pre-commit gate verifies consistency.

## 2. Hooks

Kiro hooks are in `.kiro/hooks/`; git hooks are installed with `python tools/governance/agl_governance.py install-git-hooks` (this writes `.git/hooks/pre-commit` and `post-commit`; it does not change git configuration and does not overwrite foreign hooks).

| Hook | Mechanism | What it does |
|---|---|---|
| A. After code modification | Kiro `PostToolUse` on file-writing tools (agent prompt) | Tells the agent to run `agl_governance.py impact`: affected areas and code topics, version-increment need, documentation to update, tests to run or extend, stale comments. Kiro does not forward command output for `PostToolUse`, so this hook is a prompt that makes the agent run the command. |
| B. Documentation reminder | Kiro `UserPromptSubmit` (command `agl_governance.py docs --hook`) | When the working tree has uncommitted functional changes, lists the documents that must be verified or updated in the same task (installation, device guide / HOW_TO, architecture, configuration, release notes, troubleshooting, change register). Silent otherwise. |
| C. Before commit | git `pre-commit`, and Kiro `PreToolUse` on the shell tools (command `agl_governance.py hook-pretool`) | Runs the quality gate on the staged change and blocks the commit on any FAIL. The Kiro hook also asks for explicit approval before `git push`, `gh release create` or `publish_ota_release.ps1`. A tree that passed through the Kiro hook is not re-checked by the git hook. |
| D. After commit | git `post-commit` | Records the commit (hash, application and package version, change ids, files, documentation files, quality-gate result with test summary) as a git note under `refs/notes/agrilens` (`git notes --ref=agrilens show <commit>`), and lists outstanding actions. Never pushes. |

Kiro hook notes: Kiro loads hook files at session start, so a new or changed hook takes effect in the next session. The hook commands are small Python launchers that find the repository with `git rev-parse --show-toplevel`. They fail open: if the tool or the repository cannot be found they allow the action (the git hooks still enforce the gate). Only the tool's dedicated exit code 3 is turned into Kiro's blocking exit code 2, so a broken path can never block every shell command.

Exceptions: a check that must be overridden is recorded with its reason in `tools/governance/governance_rules.json` (for example `secret_allowlist`, `bom_exceptions`, `large_file_allowed`) in a commit whose change-register entry states the exception. Commits are not made with `--no-verify`.

## 3. Quality gate

`python tools/governance/agl_governance.py check --staged` (pre-commit) or `check --full` (pre-release). Output is a PASS / FAIL / WARN / SKIP table; any FAIL gives exit code 1. The last result is kept in `.git/agrilens/last_check.json`. The gate reads files and builds the package only in a temporary copy; it never changes production configuration, `AGRILENS_RaspberryPi/` or deployed files.

| Section | Checks |
|---|---|
| repository | staged / working-tree state, temporary, debug and generated junk, large files (models and CAD allowed), UTF-8, BOM, malformed characters, LF where devices need it, secrets and credentials, local machine paths and e-mail addresses in added lines (warning), whitespace and conflict markers, changes to frozen artefacts (warning) |
| version | semantic version, derived constants, markers, release notes, package version not ahead, increment for shipped changes, release record |
| package | `SHA256SUMS`, unlisted files, `RELEASE_MANIFEST.json` against `main.py` and the model |
| code | Python syntax, ruff (rules in `pyproject.toml`), `bash -n` for shell scripts, JSON syntax; type checking is not configured (reported as SKIP) |
| model | `MODEL_SHA256` matches a model in `models/`, label count, class order equal to the production labels, registry and manifest consistency, gate constants equal to the frozen calibration; full mode also loads the ONNX file, checks input 3×224×224 and output width, and runs a sanity inference |
| documentation | HOW_TO index (existence, paths, UTF-8, no BOM, no malformed characters, up to date), broken references in current documents, unindexed documents, references to unreleased versions; staged mode also requires a complete change-register entry and the relevant documentation for functional changes |
| register | entries parse, unique ascending ids, valid categories, complete fields, commit ids recorded |
| packaging | builder pre-checks; full mode builds the package in a temporary copy, compares it byte-for-byte with the committed package when the versions are equal, and checks for unwanted files |
| tests | the whole pytest suite (unit, integration, OTA, rollback, camera with a mocked OpenCV, model contract, configuration, start-up harness); documentation-only commits skip it and say so |

Development environment for the gate: `python -m venv .venv` and `.venv/Scripts/python -m pip install -r requirements-dev.txt` (Linux: `.venv/bin/python`). The hooks use `.venv` when it exists; the environment variable `AGRILENS_GOV_PYTHON` can name another interpreter for the test and lint runs. Missing tools (ruff, pytest, onnxruntime) are reported as FAIL, never skipped silently.

Commands that target another repository (the tool call's working directory or `git -C <path>`) are checked by that repository's own governance tool; a repository without it is not checked by the Kiro hook.

## 4. Change register

`documentation/CHANGE_REGISTER.md`. Every commit that changes anything other than documentation adds an entry; the pre-commit gate refuses the commit otherwise. Create the skeleton with `agl_governance.py register new --title "..." --category "Feature; UI/UX"` and replace every `TODO`.

Fields: Date, Application version (with the increment and its rationale, or "unchanged: <reason>"), Category (`Feature`, `Bug fix`, `AI/model`, `UI/UX`, `Hardware`, `Security`, `Performance`, `DevOps/OTA`, `Documentation`, `Dataset/training`, `Tooling`), Description, Reason, Files affected, Tests executed, Test outcome, Documentation updated (or "None required: <reason>"), Known risks, Commit.

Test results are copied from an actual run, never assumed. The commit id of an entry is not known before the commit: it stays `pending` and is filled in by `agl_governance.py register sync` with the next change. The git note written by the post-commit hook records the machine-checked result for each commit.

## 5. Documentation rules

1. Update the relevant documentation in the same task; `agl_governance.py impact` and the Kiro hooks name it.
2. Do not leave documentation that describes the previous behaviour.
3. One canonical document per topic; link to it instead of copying. The canonical documents are listed in the `HOW_TO.md` index.
4. Verify commands and paths before writing them.
5. Distinguish implemented from planned, and tested from untested functionality.
6. Do not claim hardware validation that has not been performed, or model accuracy beyond the evaluation evidence.
7. Name limitations and experimental features.
8. Release records, evaluation results, dataset provenance, rollback records and licences are not edited or deleted; corrections go into a dated section or the change register.
9. New documents are added to `documentation_index` in `tools/governance/governance_rules.json`; then `agl_governance.py index --write` regenerates the index in `HOW_TO.md`.
10. `deployment/raspberry_pi/HOW_TO_RUN_ON_RASPBERRY_PI.md` is shipped to kiosks; changing it is a shipped change and needs an application version increment.

## 6. Engineering rules

Read the relevant code and documents before editing; keep changes small and backward compatible; reuse existing modules; no hard-coded machine paths in code; no credentials in the repository. Never push, publish, tag a release, trigger OTA or change a Raspberry Pi installation without explicit approval. Frozen datasets and test data are not modified and are never used to tune models or thresholds. Training and experimental work belong to the separate Model Trainer Program (`<AGRILENS_5.0.0>\Model_Trainer_Program\trainer\`), which is never installed on a kiosk; models enter this repository only as labelled candidates in `models/candidates/`.
